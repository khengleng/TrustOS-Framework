# Simulation and performance results

Both sets of numbers are generated by the tests that produce them and written to JSON, so this page
and the runs cannot disagree. Regenerate with `npx vitest run apps/merchant-wallet-basic`.

## Simulation

Product: `merchant-wallet-basic@1.0.0`. Seed 1, deterministic. Scenario mix: 2% limit exceeded, 1%
risk rejection, 1% provider timeout, 0.5% settlement failure, 0.5% reconciliation mismatch. Every
fiftieth transaction is a duplicate.

### Per-transaction mode

Limit consumption reset between transactions, so each is measured on its own. This is what the CLI
does, and it measures the product's per-transaction logic.

### Why both are reported

The pilot's first simulation run reported 9% success and looked like a broken product. It was one
simulated day containing a hundred thousand payments against a 5,000 daily limit — correct, and
swamping every other signal.

Neither number is "the" success rate. Per-transaction measures the product's logic; cumulative
measures what a daily ceiling does to a day's traffic. Reporting one without the other would be
misleading in a different direction each time.

### The simulator's own caveats

Emitted with every report, quoted here verbatim because a benchmark without its caveats is a
benchmark that gets quoted as a production figure:

> Every provider is a mock that returns immediately. The block latencies measure the runtime's own
> overhead and say nothing about a provider or a network.

> Limit consumption was cleared between transactions, so each one was measured on its own.
> Cumulative limits — daily, monthly, velocity — therefore refused nothing, and a zero in "limit
> refusals" says nothing about how they behave over a real day.

> The success rate is a rate under the injected scenario mix. With no scenarios injected it
> measures the product's internal logic and is not a reliability estimate.

> Fees are computed by the sandbox's placeholder rate, not by the product's fee schedule. Use
> `@trustsystem/fees` for a priced figure.

The last one matters for reading the fee totals above: they are the sandbox's rate, not the pilot's
0.50% schedule. The pilot's own fee arithmetic is verified in
[`financial-integrity.md`](financial-integrity.md).

## Performance

**What this measures:** the pilot's payment path in one Node process against in-memory stores —
validation, limit consume, fee calculation, ledger posting, wallet balance derivation.

**What it does not measure:** HTTP, TLS, JSON parsing, connection pooling, database round trips,
network latency, or any real provider.

Environment: Apple M4 Pro, 12 cores, 48GB, Node v20.19.1, darwin arm64.

### These numbers move, and by how much

The same suite on the same laptop has produced **4,686/s** and **6,512/s** at ten concurrent
merchants, and **5,265/s** to **9,257/s** at a hundred, depending on what else the machine was
doing. That is a spread of roughly 1.8×.

So the table above is _one run_, produced deliberately by `npm run evidence` with nothing else
competing — not the last run that happened to overwrite the file. An ordinary `npm test` no longer
writes it, because it used to, and the committed artefact then drifted from the prose quoting it on
every run.

Treat the magnitude as an order of magnitude. What is stable across every run is the shape: zero
errors, and latency growing roughly linearly with concurrency.

### The only assertion that is machine-independent

Ten times the concurrency does not cost far more than ten times the work. A quadratic term there
would be a shared structure rescanned per request, and it would be invisible at one user.

The tests assert that ratio and deliberately assert **no latency threshold** — a threshold asserted
here would be a threshold measured on whichever machine ran CI.

### How to read these numbers

They say the application logic is not the bottleneck. They say nothing about production, and a
production p95 will be larger by an amount dominated by the database and the network — the two
things this measurement excludes.

That is why the readiness scorecard marks Performance **PARTIAL** rather than PASS.
